How the field emission display works

applications/field_emission/ plots cavity amplitude against decarad radiation readings, one plot per cavity, for past measurement runs. This page covers what the display reads, where each run's data comes from, and how the data cache is built and fails.

1. What the display shows

Pick a cryomodule, one or more measurement runs, cavities, decarad channels, and a readout type. Each plot puts cavity amplitude on the x-axis and one point series per decarad channel on the y-axis.

What it does to the data before you see it

Rows under 4 MV are dropped. Any sample where AACTMEAN is below AMPLITUDE_THRESHOLD = 4 is masked out of both the plot and the fit. field_emission/constants.py::AMPLITUDE_THRESHOLD “AMPLITUDE_THRESHOLD = 4”, field_emission/measurements.py::get_columns “df.mask(df.iloc[:, 0]”

The optional fit line is rad = C1 · E2.5 · exp(−C2 / E), with E the amplitude in MV, fitted per channel with scipy.optimize.curve_fit (5500 evaluations max). Channels with fewer than 2 nonzero points, or that don't converge, get no line. The legend shows C1 and C2. plot_me.py::fit_equation “c1 * (amp**2.5) * np.exp((-c2) / amp)”, plot_me.py::add_poly_fit “skip fitting when less than two samples”, field_emission/constants.py::NUM_FIT_ITERATIONS “NUM_FIT_ITERATIONS = 5500”

No background is subtracted. The dose is plotted and fitted as archived. The linac model subtracts a fixed background before using a reading (0.8 for GAMMAAVE, 8 for GAMMA_DOSE_RATE). Quench processing uses the subtracted GAMMA_DOSE_RATE. Field emission does not subtract either. linac_utils.py::DECARAD_BACKGROUND_READING_AVG “DECARAD_BACKGROUND_READING_AVG = 0.8”, linac_utils.py::DECARAD_BACKGROUND_READING_RAW “DECARAD_BACKGROUND_READING_RAW = 8”, quench_processing/quench_cavity.py “if self.decarad.max_raw_dose”

CHECK: where does this fit form come from, and is 2.5 the intended exponent? Nothing in the repo cites a source.
CHECK: should the fit use background-subtracted dose? That would change C1 and C2.
CHECK: is 4 MV the right "cavity is on" cutoff for every cryomodule, including LCLS-II-HE?

Which channel is which

There are two decarads, each with 10 heads sc_linac/decarad.py::Decarad “for head in range(1, 11)”. CHECK, from the SRF group, no document: one head sits at each end of the cryomodule and one at each cavity's tuner access port, and the decarads are wheeled between cryomodules and set up per run. The archived POSN history below does show them moving. So channel n is not tied to any cavity. The run list records which decarad was used, not how it was set up, and the display plots every selected channel against every selected cavity. Read the run's elog to know which head a channel was.

Each head has a text PV naming its position, for example RADM:SYS0:100:01:POSN = "US of Cavity 1, CM01", but those are not archived, so past runs can't be read back from them. Each decarad's own RADM:SYS0:{n}00:POSN is archived and holds a cryomodule number. It matched the run list's cryomodule for 76 of 80 runs.

Cavities in one run can overlap in time. In CM06's 2024-02-02 run, CAV3, CAV4 and CAV7 were all above 4 MV at once, so a channel plotted against one of them can include radiation from the others.

A run is one row of the run list: a cryomodule, a start and end time, which decarad was used, and an elog link. Everything else is fetched.

Three runs looked wrong:

  • CM27, dated 2026-10-16: 1 row in all 16 datasets, and no cavity ever above 4 MV. The date was a typo for 2024 (same elog ID as CM27's other 10/16/24 run), so the archiver was asked about a window in the future. The run list in git has the corrected date.
  • CM04 2023-10-25, CAV5 instant: 1 row. The align step drops a timestamp until all 11 PVs have had at least one value, so one sparse PV can shrink a whole dataset. Here it was CAV5's own AACTMEAN: the other 7 cavities' instant datasets use the same 10 decarad PVs and have about 6,900 rows each, and CAV5's average is short too. The one value is 0.004 MV, so CAV5 was off and nothing above 4 MV was lost.
  • CM01 2023-10-02: channel 1 read up to about 88 between 09:39 and 09:41 while every cavity in CM01–CM05, H1, H2 and CM35 was below 4 MV. Decarad 1's POSN read 35 for the whole run and only changed to 1 at 10:55. CHECK: was decarad 1 at CM01 during this run, and what caused the spike?

3. How the cache gets built

Only the run list is in git. The cache lives in the shared SRF directory (/home/physics/srf/field_emission/ on Linux). platform_paths.py::get_srf_base_dir “Path("/home/physics/srf")”, platform_paths.py::get_field_emission_dir “/ "field_emission"”, field_emission/constants.py::H5_PATH

Every time the display opens, it starts a background sync, and keeps the selection panel disabled until the sync ends. field_emission_gui.py::FieldEmission.start_cache_sync “self.left_panel.setEnabled(False)” 

missing = find_missing_runs(run list)        # compare run list to cache

for run in missing:
    16 × (archiver fetch → align → write CSV)
    write every CSV on disk into the HDF5    # this run's, plus any leftovers
    delete every CSV it wrote in, once the file has closed
    # any exception stops the sync here; runs already written stay

gui_updater.py::sync_cache “convert_to_h5(lookup)”, update_h5py.py::convert_to_h5 “os.remove(csv_path)”

Each run takes a minute or two. A full build of all 80 runs took 1.75 hours on site (2026-10-05), and matched kvetta's original file for every run except the corrected CM27 one. Build it once without the display, and after that each open only fetches new runs: 

python -m sc_linac_physics.applications.field_emission.gui_updater

Re-fetching a run replaces its datasets rather than reusing them, since the archiver can return a different row count. update_h5py.py::_write_dataset_with_attributes “del group[readout]”

4. What counts as "already cached"

find_missing_runs skips a run only when all 8 CAV{n} groups exist, each with average and instant. A run left half-written by an interrupted sync is fetched again on the next open.

update_h5py.py::_run_is_complete “for readout in RAD_READ_TYPES”

Why empty datasets still count

A run with genuinely no data is never re-fetched in a loop. For a PV with no samples in the window, lcls_tools returns an empty result rather than raising. That still writes a CSV, and an empty CSV still becomes a dataset, so the run counts as complete. The sync re-fetches a whole run only when one of its datasets was never written, which takes a crash. Timeouts, connection failures and HTTP errors do raise and stop the sync; the run being fetched is retried next open. lcls_tools: get_values_over_time_range, the “if pv not in result” fill-in

What the cache rule doesn't catch

A run is keyed only by cryomodule and start time. Editing a run-list row in any other way (end time, decarad, notes) doesn't trigger a re-fetch. Re-fetching also never updates a run's attrs: they are written once and skipped after that. To pick up an edited row, delete the cache file. update_h5py.py::_run_is_complete, update_h5py.py::_set_metadata_attributes “"cryomodule" not in group.attrs”

One empty PV empties the whole dataset. The align step drops every row with a missing value, so a channel with no samples leaves 0 rows. All 8 cavities share the same 10 decarad PVs, so one unarchived channel blanks all 8 datasets for that readout. None of kvetta's 80 runs hit this. amp_vs_radiation.py::align_pvs_to_common_time “dropna(how="any")”

The simulator writes a run's datasets in fetch order. The real order is whatever glob returns, which isn't sorted. That changes which datasets land before a crash, not whether a run ends up partial. update_h5py.py::convert_to_h5

The failure the simulator can't show

HDF5 has no journal. If the process dies while writing a run, the file can be left unreadable, not just incomplete. On the next open, the sync fails first and shows "Data cache not updated". Then picking a cryomodule raises, because match_measurement_dates only handles a missing file (FileNotFoundError). The fix today is deleting the file, after which the next sync rebuilds it. The write takes seconds per run, against minutes of fetching, so the window is small, but it reopens on every run of a long build. field_emission/measurements.py::match_measurement_dates “except FileNotFoundError”
