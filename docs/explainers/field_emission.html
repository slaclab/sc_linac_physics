How the field emission display works

applications/field_emission/ plots cavity amplitude against decarad radiation readings, one plot per cavity, for past measurement runs. This page covers what the display reads, where each run's data comes from, and how the data cache is built and fails.

1. What the display shows

Pick a cryomodule, one or more measurement runs, cavities, decarad channels, and a readout type. Each plot puts cavity amplitude on the x-axis and one point series per decarad channel on the y-axis.

PVNotes
x: amplitude ACCL:{linac}:{cm}{cav}0:AACTMEAN MV, all 8 cavities, whichever one was being run amp_vs_radiation.py::build_amplitude_pvs “+ "AACTMEAN"”, field_emission/constants.py::CAVITIES “CAVITIES = 8”
y: radiation, "average" RADM:SYS0:{n}00:{ch:02d}:GAMMAAVE decarad n is 1 or 2, channels 01–10 amp_vs_radiation.py::build_decarad_pvs “RADM:SYS0:{decarad}00:”, amp_vs_radiation.py::build_rad_readout_pvs “{sel_rad_channel:02d}:GAMMAAVE”, field_emission/constants.py::RAD_CHANNELS “RAD_CHANNELS = 10”
y: radiation, "instant" RADM:SYS0:{n}00:{ch:02d}:GAMMA_DOSE_RATE amp_vs_radiation.py::build_rad_readout_pvs “{sel_rad_channel:02d}:GAMMA_DOSE_RATE”

Every PV is read from the archiver, never live. The display writes no PVs. amp_vs_radiation.py::fetch_pv_data → lcls_tools get_values_over_time_range

Two things it does to the data before you see it

Rows under 4 MV are dropped. Any sample where AACTMEAN is below AMPLITUDE_THRESHOLD = 4 is masked out of both the plot and the fit. field_emission/constants.py::AMPLITUDE_THRESHOLD “AMPLITUDE_THRESHOLD = 4”, field_emission/measurements.py::get_columns “df.mask(df.iloc[:, 0]”

The optional fit line is rad = C1 · E2.5 · exp(−C2 / E), with E the amplitude in MV, fitted per channel with scipy.optimize.curve_fit (5500 evaluations max). Channels with fewer than 2 nonzero points, or that don't converge, get no line. The legend shows C1 and C2. plot_me.py::fit_equation “c1 * (amp**2.5) * np.exp((-c2) / amp)”, plot_me.py::add_poly_fit “skip fitting when less than two samples”, field_emission/constants.py::NUM_FIT_ITERATIONS “NUM_FIT_ITERATIONS = 5500”

CHECK: where does this fit form come from, and is 2.5 the intended exponent? Nothing in the repo cites a source.
CHECK: is 4 MV the right "cavity is on" cutoff for every cryomodule, including LCLS-II-HE?
CHECK: where are decarads 1 and 2 physically, relative to each cryomodule? The code takes the number from the run list and does nothing else with it.

2. Where one run's data comes from

A run is one row of the run list: a cryomodule, a start and end time, which decarad was used, and an elog link. Everything else is fetched.

Two runs looked wrong, and both are explained by the steps above:

  • CM27, dated 2026-10-16: 1 row in all 16 datasets, and no cavity ever above 4 MV. The date was a typo for 2024 (same elog ID as CM27's other 10/16/24 run), so the archiver was asked about a window in the future. The run list in git has the corrected date.
  • CM04 2023-10-25, CAV5 instant: 1 row. The align step drops a timestamp until all 11 PVs have had at least one value, so one sparse PV can shrink a whole dataset. Here it was CAV5's own AACTMEAN: the other 7 cavities' instant datasets use the same 10 decarad PVs and have about 6,900 rows each, and CAV5's average is short too. The one value is 0.004 MV, so CAV5 was off and nothing above 4 MV was lost.

3. How the cache gets built

Only the run list is in git. The cache lives in the shared SRF directory (/home/physics/srf/field_emission/ on Linux). platform_paths.py::get_srf_base_dir “Path("/home/physics/srf")”, platform_paths.py::get_field_emission_dir “/ "field_emission"”, field_emission/constants.py::H5_PATH

Every time the display opens, it starts a background sync, and keeps the selection panel disabled until the sync ends. field_emission_gui.py::FieldEmission.start_cache_sync “self.left_panel.setEnabled(False)” 

missing = find_missing_runs(run list)        # compare run list to cache

for run in missing:                          # phase 1: fetch
    16 × (archiver fetch → align → write CSV)
    # any exception stops the sync here, and phase 2 never runs

if missing:                                  # phase 2: convert
    for csv in CSV_OUTPUT_DIR/*.csv:         # every CSV on disk, old ones too
        write it into the HDF5 as one dataset

gui_updater.py::UpdateWorker.sync_update “if missing:”, update_h5py.py::convert_to_h5 “glob.glob(os.path.join(CSV_OUTPUT_DIR, "*.csv"))”

Two details matter for what follows:

  • CSVs are never deleted. Phase 2 converts every CSV in the directory, including ones left over from an earlier sync that failed.
  • Phase 2 only runs if something was missing. If nothing is missing, leftover CSVs just sit there.

4. What counts as "already cached"

find_missing_runs skips a run only when all 16 of its datasets exist (rule B below). Rule A was the simpler alternative:

Rule A: group existsRule B: group is complete
Skip a run when CM01/2023-10-02_0913 exists it has all 8 CAV{n}, each with average and instant
A half-written run stays half-written, unless an unrelated sync happens to sweep up its leftover CSVs gets re-fetched next time the display opens
Cost a group lookup per run 16 dataset lookups per run, still a fraction of a second for 80 runs

update_h5py.py::_run_is_complete “for readout in RAD_READ_TYPES”

Why empty datasets still count

A run with genuinely no data is never re-fetched in a loop. For a PV with no samples in the window, lcls_tools returns an empty result rather than raising. That still writes a CSV, and an empty CSV still becomes a dataset, so the run counts as complete. Rule B only re-fetches a dataset that was never written, which takes a crash. Timeouts, connection failures and HTTP errors do raise, and stop the sync in phase 1; that run is retried next open. lcls_tools: get_values_over_time_range, the “if pv not in result” fill-in

One empty PV empties the whole dataset. The align step drops every row with a missing value, so a channel with no samples leaves 0 rows. All 8 cavities share the same 10 decarad PVs, so one unarchived channel blanks all 8 datasets for that readout. None of kvetta's 80 runs hit this. amp_vs_radiation.py::align_pvs_to_common_time “dropna(how="any")”

The simulator converts CSVs in run order. The real order is whatever glob returns, which isn't sorted. That changes which datasets land before a crash, not whether a run ends up partial. update_h5py.py::convert_to_h5

The failure the simulator can't show

HDF5 has no journal. If the process dies during phase 2, the file can be left unreadable, not just incomplete. The display then raises on open, because match_measurement_dates only handles a missing file (FileNotFoundError). The fix today is deleting the file, after which the next open rebuilds it. Closing the display during the first build, which writes all 80 runs, is the likely way to hit this. field_emission/measurements.py::match_measurement_dates “except FileNotFoundError”
